# ربات آگهی‌های جدید خودرو دیوار — نسخه کد (Python)

بازنویسی پروژه [divar-bot](../divar-bot/README.md) از **n8n** به یک بک‌اند اختصاصی با **Python**.
همه قابلیت‌های نسخه n8n حفظ می‌شود (Mini App، بازه زمانی، Backfill، اشتراک، حذف تکراری، گروه‌بندی جستجوها) و چند محدودیت آن نسخه هم برطرف می‌شود.

**رفتار اصلی ربات:**
1. بعد از ساخت فیلتر، **همه** آگهی‌های مطابق در بازه زمانی فیلتر پیدا می‌شوند و صفحه‌به‌صفحه (۱۰ تایی) به کاربر نشان داده می‌شوند.
2. از آن به بعد، هر ۱۰ دقیقه فقط آگهی‌های **جدید** مطابق ارسال می‌شوند.
3. اگر آگهی‌ای که قبلاً ارسال شده **ویرایش** شود (تغییر قیمت، توضیحات، حذف)، ربات بسته به نوع تغییر یا اعلان می‌دهد (کاهش قیمت) یا پیام قبلی را بی‌صدا به‌روز می‌کند.

مخاطب اصلی: بنگاه‌داران خودرو و خریدارانی که می‌خواهند آگهی‌های مناسب را زودتر از بقیه ببینند.

## چرا از n8n به کد؟

| مشکل در نسخه n8n | راه‌حل در نسخه کد |
|---|---|
| حذف تکراری با حافظه نود «Remove Duplicates» → آگهی ارسال‌شده در Backfill ممکن بود دوباره توسط Crawler ارسال شود | جدول `deliveries` با کلید یکتای `(user_id, post_token)` → **هیچ آگهی‌ای دو بار به یک کاربر نمی‌رسد** |
| Crawler فقط صفحه اول (~۲۵ آگهی) را می‌دید → در شهرهای پرآگهی احتمال از دست رفتن آگهی | صفحه‌زنی تا رسیدن به آخرین آگهی دیده‌شده (با سقف صفحه) |
| Backfill حداکثر ۲۰ آگهی می‌فرستاد (از ~۱۵۰ آگهی بررسی‌شده) | **همه** آگهی‌های بازه زمانی پیدا می‌شوند و با دکمه «۱۰ آگهی بعدی» صفحه‌به‌صفحه نمایش داده می‌شوند |
| تغییر آگهی بعد از ارسال (قیمت، حذف) نادیده گرفته می‌شد | تشخیص تغییر + اعلان کاهش قیمت + به‌روزرسانی بی‌صدای پیام قبلی |
| مدیریت کاربران فقط از طریق Data tables در n8n | دستورهای ادمین داخل خود ربات + گزارش آمار |
| منطق پخش‌شده در چند نود Code، بدون تست | ماژول‌های جدا با **تست واحد** (مخصوصاً Matcher) |
| محدودیت مقیاس (چند صد کاربر) | async + PostgreSQL + صف ارسال → هزاران کاربر |
| وابستگی به تونل/‌Webhook برای تست | در توسعه با **Polling** اجرا می‌شود؛ نیازی به HTTPS نیست |
| نسخه‌بندی سخت (JSON workflow) | کد در git، مهاجرت دیتابیس با Alembic |

## استک فنی

| بخش | ابزار | دلیل |
|---|---|---|
| زبان | **Python 3.12** | اکوسیستم خوب برای ربات و اسکرپینگ |
| ربات تلگرام | **aiogram 3** | async، روتر، فیلترها، پشتیبانی کامل از WebApp |
| HTTP به دیوار | **httpx (async)** + **tenacity** | درخواست همزمان کنترل‌شده، retry با backoff |
| زمان‌بندی | **APScheduler** (AsyncIOScheduler) | اجرای Crawler هر ۱۰ دقیقه داخل همان پروسه |
| دیتابیس | **PostgreSQL 16** + **SQLAlchemy 2 (async)** + **asyncpg** | پایدار، قفل و کلید یکتا برای حذف تکراری |
| مهاجرت دیتابیس | **Alembic** | تغییر جدول‌ها بدون از دست دادن داده |
| تنظیمات | **pydantic-settings** | خواندن `.env` با اعتبارسنجی نوع |
| سرو Mini App | **aiohttp web** (همان سروری که aiogram برای Webhook دارد) | بدون نیاز به سرور جدا |
| لاگ | **structlog** یا `logging` استاندارد | لاگ ساخت‌یافته برای عیب‌یابی |
| تست | **pytest** + **pytest-asyncio** + **respx** | Mock کردن پاسخ‌های دیوار |
| استقرار | **Docker** + **docker compose** | یک دستور برای بالا آوردن کل سیستم |

> برای مقیاس خیلی بزرگ (چند هزار فیلتر فعال) می‌توان APScheduler را با **Celery/arq + Redis** جایگزین کرد. برای شروع لازم نیست.

## معماری کلی

یک پروسه Python (یک کانتینر) که سه بخش را همزمان اجرا می‌کند، به‌علاوه PostgreSQL:

```
                                   👤 کاربر در تلگرام
                ┌─────────────────────────┼──────────────────────────┐
     پیام/دکمه  │           دکمه «➕ فیلتر جدید»                        │
                │                         ▼                            │
                │        ┌────────────────────────────────┐            │
                │        │ Mini App (webapp/filter.html)  │◄── سرو شده توسط aiohttp
                │        └───────────────┬────────────────┘
                │          tg.sendData() │
                ▼                        ▼
┌──────────────────────────────── app (Python, asyncio) ─────────────────────────────┐
│                                                                                    │
│  ┌──────────────────────┐   فیلتر جدید   ┌──────────────────────┐                  │
│  │ bot/  (aiogram)      │───────────────►│ services/backfill.py │──┐               │
│  │ هندلرها، کیبوردها    │  asyncio task  └──────────────────────┘  │               │
│  └──────────┬───────────┘                                          │               │
│             │                                                      ▼               │
│  ┌──────────┴───────────┐   هر ۱۰ دقیقه  ┌──────────────────────┐  ┌────────────┐  │
│  │ scheduler (APS)      │───────────────►│ services/crawler.py  │─►│ sender     │──┼─► Telegram
│  └──────────────────────┘                └──────────┬───────────┘  │ (صف + rate │  │
│                                                     │              │  limit)    │  │
│                                          ┌──────────▼───────────┐  └────────────┘  │
│                                          │ divar/client.py      │──────────────────┼─► api.divar.ir
│                                          │ divar/parser.py      │                  │
│                                          │ core/matcher.py      │                  │
│                                          └──────────────────────┘                  │
└────────────────────────────────────────────┬───────────────────────────────────────┘
                                             │ SQLAlchemy (async)
                                             ▼
                        ┌──────────────────────────────────────────┐
                        │ 🗄 PostgreSQL                             │
                        │ users · filters · posts · deliveries ·   │
                        │ post_changes                             │
                        └──────────────────────────────────────────┘
```

**اصول کلیدی:**
- **Matcher و Planner توابع خالص هستند** (بدون I/O)؛ ورودی آگهی + فیلتر، خروجی true/false. پس کاملاً قابل تست‌اند و Crawler و Backfill از **یک** منطق استفاده می‌کنند.
- **Divar Client تنها نقطه تماس با دیوار است**؛ اگر API دیوار عوض شد فقط `divar/` تغییر می‌کند.
- **Sender تنها نقطه ارسال پیام است**؛ محدودیت سرعت تلگرام، خطای 429 و کاربر بلاک‌کرده فقط اینجا مدیریت می‌شود.
- **هر ارسال قبل از فرستادن در `deliveries` ثبت می‌شود** (INSERT … ON CONFLICT DO NOTHING)؛ اگر ردیف از قبل بود، ارسال نمی‌شود.
- **هر آگهی یک «اثر انگشت» (fingerprint) دارد**؛ هر بار که دوباره دیده شود مقایسه می‌شود و تغییرات در `post_changes` ثبت و به `services/changes.py` سپرده می‌شوند.

## نگاشت Workflowهای n8n به ماژول‌های کد

| n8n | کد | توضیح |
|---|---|---|
| Workflow 0 — Setup Tables | `alembic/versions/*` | `alembic upgrade head` جدول‌ها را می‌سازد |
| Workflow 1 — Telegram Bot | `app/bot/handlers/*.py` | هر دستور یک هندلر؛ نود Decide به چند هندلر کوچک شکسته می‌شود |
| Workflow 2 — Filter Form (قدیمی) | — | حذف می‌شود |
| Workflow 3 — Crawler | `app/services/crawler.py` | job زمان‌بندی‌شده APScheduler |
| Workflow 4 — Mini App Page | `app/web/server.py` + `webapp/` | route استاتیک aiohttp |
| Workflow 5 — Backfill | `app/services/backfill.py` | `asyncio.create_task` بعد از ذخیره فیلتر؛ این بار **همه** آگهی‌ها + صفحه‌بندی |
| — (جدید) | `app/services/changes.py` + `app/core/diff.py` | تشخیص و مدیریت ویرایش آگهی‌های ارسال‌شده |
| نود Config | `.env` + `app/config.py` | |
| Data table `divar_users` | جدول `users` | |
| Data table `divar_filters` | جدول `filters` | |
| حافظه Remove Duplicates | جدول‌های `posts` و `deliveries` | |

## مدل داده (PostgreSQL)

### `users`

| ستون | نوع | توضیح |
|---|---|---|
| `id` | bigint PK | |
| `chat_id` | bigint UNIQUE | شناسه تلگرام |
| `name` | text | نام در تلگرام |
| `username` | text null | |
| `expires_at` | timestamptz null | پایان اشتراک (null = نامحدود) |
| `max_filters` | int | سقف فیلتر (پیش‌فرض از `.env`) |
| `plan` | text | `trial` / `basic` / `pro` (برای فازهای بعد) |
| `is_blocked` | bool | کاربر ربات را بلاک کرده → به او ارسال نمی‌شود |
| `is_admin` | bool | |
| `created_at` | timestamptz | |

### `filters`

| ستون | نوع | توضیح |
|---|---|---|
| `id` | bigint PK | شماره فیلتر در دستورهای `/del_12` و … |
| `user_id` | FK → users | صاحب فیلتر (ON DELETE CASCADE) |
| `name` | text | |
| `city_id` | int | کد شهر دیوار |
| `brand` | text null | کلید انگلیسی برند (مثل `Dena`)؛ null = همه |
| `min_year` / `max_year` | int null | null = بدون محدودیت |
| `max_mileage` | int null | کیلومتر |
| `min_price` / `max_price` | bigint null | تومان |
| `gearbox` | text null | `automatic` / `manual` / null |
| `include_kw` | text[] | حداقل یکی باید باشد |
| `exclude_kw` | text[] | هیچ‌کدام نباید باشد |
| `max_age_days` | int | ۱ تا ۶۰، پیش‌فرض ۳ |
| `change_alerts` | text | `price_drop` (پیش‌فرض) / `all` / `none` — رفتار هنگام ویرایش آگهی‌های ارسال‌شده |
| `active` | bool | |
| `created_at` / `updated_at` | timestamptz | |

> تفاوت با n8n: کاربر با `user_id` (FK) ارتباط دارد نه `chat_id` رشته‌ای؛ کلمات کلیدی آرایه‌اند نه رشته با ویرگول؛ «بدون محدودیت» = `NULL` به‌جای `0`.

### `posts` — کش آگهی‌های دیده‌شده

| ستون | نوع | توضیح |
|---|---|---|
| `token` | text PK | شناسه آگهی دیوار |
| `city_id`, `brand` | | |
| `title`, `description` | text | |
| `price` | bigint null | |
| `year`, `mileage` | int null | |
| `color`, `gearbox`, `body_status`, `engine_status` | text null | |
| `district` | text null | محله |
| `image_url` | text null | |
| `published_at` | timestamptz null | تاریخ انتشار (از جزئیات) |
| `details_fetched` | bool | جزئیات گرفته شده یا نه |
| `fingerprint` | text | هش فیلدهای مهم (قیمت، کارکرد، عنوان، توضیحات، تعداد عکس) — برای تشخیص سریع تغییر |
| `status` | text | `active` / `deleted` (حذف‌شده یا فروخته‌شده) |
| `first_seen_at` / `last_seen_at` | timestamptz | |
| `last_checked_at` | timestamptz null | آخرین باری که جزئیات دوباره گرفته شد |

فایده: جزئیات هر آگهی **فقط یک بار** از دیوار گرفته می‌شود (مگر وقتی تغییر تشخیص داده شود)، حتی اگر نردبان شود یا در Backfill کاربر دیگری ظاهر شود. `posts` همیشه **آخرین نسخه** آگهی را نگه می‌دارد.

### `deliveries` — چه آگهی‌ای به چه کسی رفته

| ستون | نوع | توضیح |
|---|---|---|
| `user_id` | FK | |
| `post_token` | FK → posts | |
| `filter_id` | FK null | فیلتری که باعث ارسال شد |
| `source` | text | `crawler` / `backfill` |
| `status` | text | `queued` (پیدا شده در Backfill، هنوز نشان داده نشده) / `pending` / `sent` / `listed` (فقط در فهرست خلاصه آمده) / `failed` |
| `found_at` | timestamptz | زمان پیدا شدن (ترتیب صفحه‌بندی) |
| `sent_at` | timestamptz null | |
| `message_id` | bigint null | شناسه پیام تلگرام — برای reply و ویرایش پیام قبلی |
| `sent_price` | bigint null | قیمت آگهی در لحظه ارسال (مبنای محاسبه «٪ کاهش») |
| `last_notified_at` | timestamptz null | آخرین اعلان تغییر (برای cooldown) |
| **UNIQUE** | `(user_id, post_token)` | کلید حذف تکراری |

> آگهی‌های `queued` هم جزو «دیده‌شده» حساب می‌شوند؛ پس Crawler آن‌ها را دوباره به‌عنوان آگهی جدید نمی‌فرستد.

### `post_changes` — تاریخچه تغییرات آگهی‌ها

| ستون | نوع | توضیح |
|---|---|---|
| `id` | bigint PK | |
| `post_token` | FK → posts | |
| `field` | text | `price` / `mileage` / `title` / `description` / `images` / `status` |
| `old_value` / `new_value` | text | |
| `kind` | text | `price_drop` / `price_up` / `content` / `deleted` |
| `detected_at` | timestamptz | |
| `source` | text | `crawler` / `recheck` |

این جدول به‌مرور **تاریخچه قیمت** می‌سازد و در فاز ۳ برای تحلیل قیمت بازار استفاده می‌شود.

ایندکس‌ها: `filters(active)`، `filters(user_id)`، `posts(last_seen_at)`، `deliveries(status)`، `deliveries(post_token)`، `deliveries(user_id, filter_id, status, found_at)`، `post_changes(post_token, detected_at)`.

پاکسازی: یک job روزانه ردیف‌های `posts`، `deliveries` و `post_changes` قدیمی‌تر از ۹۰ روز را پاک می‌کند.

## ماژول‌ها به تفصیل

### ۱. `divar/client.py` — DivarClient

```python
class DivarClient:
    async def search(self, body: dict, pagination: dict | None = None) -> SearchPage: ...
    async def get_post(self, token: str) -> dict | None: ...
```

- یک `httpx.AsyncClient` مشترک با `User-Agent` مرورگر، timeout ده‌ثانیه‌ای و HTTP/2.
- **Rate limiter سراسری**: قبل از هر درخواست حداقل `DIVAR_REQUEST_DELAY + random(0, DIVAR_JITTER)` ثانیه فاصله. Crawler و Backfill از **یک** نمونه client استفاده می‌کنند تا مجموع درخواست‌ها کنترل شود.
- **Retry** با tenacity: برای timeout و کدهای 429 و 5xx، سه بار با backoff نمایی. خطای 4xx دیگر retry نمی‌شود.
- اگر چند بار پشت سر هم 403/429 آمد، **circuit breaker** چند دقیقه درخواست‌ها را متوقف می‌کند و به ادمین پیام می‌دهد.

### ۲. `divar/parser.py`

- `parse_search(json) -> list[ListItem]`: توکن، عنوان، قیمت و کارکرد (از متن‌های لیست)، تصویر، محله، و «x دقیقه پیش».
- `parse_post(json) -> PostDetails`: همه فیلدهای جزئیات (سال، رنگ، گیربکس، وضعیت موتور و بدنه، تاریخ انتشار، توضیحات، تعداد عکس).
- اعداد فارسی/عربی را تبدیل می‌کند (`core/persian.py`).
- **پارسر نباید کرش کند**: اگر فیلدی نبود `None` برمی‌گرداند و یک warning لاگ می‌کند. این اولین هشدار تغییر API دیوار است.

### ۳. `core/planner.py` — گروه‌بندی جستجوها

همان منطق «Plan Searches» در n8n:

1. فیلترهای فعالِ کاربرانی که اشتراکشان معتبر است و بلاک نکرده‌اند.
2. گروه‌بندی بر اساس کلید `(city_id, brand)`.
3. برای هر گروه یک `SearchGroup` با بدنه جستجو:
   - سال و کارکرد فقط وقتی به دیوار داده می‌شوند که **همه** فیلترهای گروه آن را داشته باشند (اجتماع بازه‌ها).
   - مرتب‌سازی بر اساس تاریخ (`sort_date`).

مثال: ۵۰ فیلتر ← ۸ جستجو.

### ۴. `core/matcher.py` — تطبیق دو مرحله‌ای

```python
def pre_match(item: ListItem, f: FilterSpec) -> bool: ...      # فقط داده‌های لیست
def full_match(post: Post, f: FilterSpec, now: datetime) -> bool: ...  # بعد از گرفتن جزئیات
```

| مرحله | کجا | شرط‌ها | هزینه |
|---|---|---|---|
| ۱ | خود دیوار (بدنه جستجو) | شهر، برند، سال*، کارکرد* | یک درخواست برای هر گروه |
| ۲ | `pre_match` | قیمت، کارکرد، کلمات حذفی (در عنوان) | بدون درخواست |
| ۳ | `full_match` | گیربکس، سال دقیق، کلمات لازم و حذفی (عنوان + توضیحات)، **بازه زمانی** | فقط برای آگهی‌های جدید |

- مقایسه کلمات بعد از **نرمال‌سازی** انجام می‌شود: «ي/ك» عربی به «ی/ک»، حذف نیم‌فاصله و اعراب، و حروف کوچک.
- بازه زمانی: اگر `published_at` از `now − max_age_days` قدیمی‌تر باشد رد می‌شود (برای آگهی‌های نردبان‌شده).
- اگر جزئیات گرفته نشد، `full_match` با داده‌های لیست تصمیم می‌گیرد و پیام با هشدار ⚠️ ارسال می‌شود.

### ۵. `services/crawler.py` — چرخه هر ۱۰ دقیقه

```
run_crawl():
  1. groups = planner.plan(active filters)
  2. برای هر group:
       a. صفحه اول جستجو؛ اگر همه آگهی‌های صفحه «جدید» بودند و صفحه بعد وجود داشت،
          صفحه بعد (تا CRAWL_MAX_PAGES) ← رفع مشکل از دست رفتن آگهی‌ها
       b. upsert آگهی‌ها در posts (last_seen_at)
       c. تشخیص تغییر (آگهی‌های قبلاً دیده‌شده): قیمت/عنوان لیست ≠ نسخه ذخیره‌شده؟
          ← get_post ← diff ← post_changes ← changes.handle_changes()   (بخش «تغییر آگهی بعد از ارسال»)
       d. برای هر آگهی و هر فیلتر گروه: pre_match
       e. آگهی‌هایی که حداقل یک فیلتر را pre_match کرده‌اند و details_fetched=false ← get_post
       f. full_match ← لیست (user, post, filter)
          (شامل آگهی‌های قدیمی که بعد از تغییر تازه وارد فیلتر شده‌اند)
  3. برای هر کاربر: هر آگهی فقط یک بار (حتی اگر چند فیلتر او جور شد)
  4. INSERT INTO deliveries … ON CONFLICT DO NOTHING RETURNING ← فقط ردیف‌های تازه به sender می‌روند
```

- job با `max_instances=1` و `coalesce=True` تعریف می‌شود تا اگر یک اجرا طول کشید، دو اجرا همزمان نشوند.
- **اجرای اول بعد از استقرار:** اگر جدول `posts` خالی باشد، Crawler فقط آگهی‌ها را ثبت می‌کند و چیزی نمی‌فرستد (حالت «warm-up»). این همان مشکل ارسال ۲۰ تا ۳۰ پیام در اجرای اول n8n را برطرف می‌کند.
- خطای یک گروه، بقیه گروه‌ها را متوقف نمی‌کند (try/except برای هر گروه + لاگ).

### ۶. `services/backfill.py`

همان Workflow 5، این بار **بدون سقف ۲۰ آگهی** و با صفحه‌بندی. جزئیات کامل در بخش [ارسال اولیه همه آگهی‌های فیلتر](#ارسال-اولیه-همه-آگهیهای-فیلتر).

```python
async def run_backfill(filter_id: int) -> None: ...                 # پیدا کردن همه + ارسال صفحه اول
async def show_next_page(user_id: int, filter_id: int) -> None: ... # دکمه «۱۰ آگهی بعدی»
async def show_summary_list(user_id: int, filter_id: int) -> None: ... # دکمه «فهرست خلاصه همه»
```

- برای جلوگیری از اجرای همزمان دو Backfill برای یک کاربر، یک `asyncio.Lock` برای هر `user_id` در نظر گرفته می‌شود.
- **Backfill هنگام ویرایش هم امن است** (به‌خاطر `deliveries`)؛ فقط آگهی‌هایی که کاربر قبلاً ندیده اضافه می‌شوند.

### ۷. `services/sender.py`

- یک `asyncio.Queue` و یک worker که پیام‌ها را می‌فرستد.
- **محدودیت‌های تلگرام**: حداکثر ~۲۵ پیام در ثانیه در کل و ~۱ پیام در ثانیه به هر چت.

- `TelegramForbiddenError` (کاربر ربات را بلاک کرده): `users.is_blocked = true` و پیام‌های بعدی او رد می‌شوند. با `/start` دوباره `false` می‌شود.

- علاوه بر ارسال، دو نوع کار دیگر هم در صف می‌آیند:
  - **reply**: پیام جدید در جواب به `message_id` قبلی (اعلان کاهش قیمت).
  - **edit**: `edit_message_caption` / `edit_message_text` روی `message_id` قبلی (به‌روزرسانی بی‌صدا).
  - اگر پیام قبلی پاک شده یا قابل ویرایش نبود (`TelegramBadRequest`)، فقط لاگ می‌شود؛ برای reply پیام بدون reply فرستاده می‌شود.
- پیام با عکس اول آگهی (`send_photo` با caption) ارسال می‌شود. اگر عکس نبود یا متن از ۱۰۲۴ کاراکتر caption بیشتر شد، `send_message` با HTML.
- دکمه‌های اینلاین زیر پیام: `🔗 مشاهده در دیوار` (URL) و `⏸ توقف این فیلتر` (callback).

## ارسال اولیه همه آگهی‌های فیلتر

وقتی کاربر فیلتر می‌سازد، باید **همه** آگهی‌های مطابق در بازه زمانی فیلتر را ببیند، نه فقط ۲۰ تای اول. ولی فرستادن مثلاً ۳۰۰ پیام پشت سر هم اسپم است و به محدودیت سرعت تلگرام می‌خورد. راه‌حل: **همه پیدا می‌شوند، ولی صفحه‌به‌صفحه نمایش داده می‌شوند.**

### جریان

```
1. پیام «🔎 در حال جستجو در ۱۶ روز اخیر...»  (همین پیام با پیشرفت ویرایش می‌شود: «صفحه ۵ — ۸۷ آگهی بررسی شد»)
2. صفحه‌زنی جستجوی دیوار تا رسیدن به تاریخ مرز (now − max_age_days) یا BACKFILL_MAX_PAGES
3. pre_match روی همه آگهی‌ها (با داده‌های لیست، بدون درخواست اضافه)
4. INSERT همه کاندیدها در deliveries با status='queued' (مرتب بر اساس جدیدترین)
5. پیام جمع‌بندی + ۱۰ کارت کامل اول (جزئیات فقط برای همین ۱۰ تا گرفته می‌شود)
6. دکمه‌ها زیر آخرین کارت:  [📄 ۱۰ آگهی بعدی (۱۳۷ باقی‌مانده)]  [📋 فهرست خلاصه همه]
```

نمونه:

```
✅ فیلتر «دنا اتومات مشهد» ذخیره شد

📦 حدود ۱۴۷ آگهی در ۱۶ روز اخیر پیدا شد
۱۰ آگهی جدیدتر در ادامه ⬇️
```

### چرا جزئیات «تنبل» (lazy) گرفته می‌شود؟

گرفتن جزئیات ۳۰۰ آگهی با فاصله ۲ ثانیه یعنی ۱۰ دقیقه انتظار و ۳۰۰ درخواست به دیوار. بنابراین:
- شمارش اولیه با `pre_match` (داده‌های لیست) انجام می‌شود، پس عدد «حدودی» است.
- جزئیات هر آگهی **فقط وقتی نوبت نمایشش برسد** گرفته می‌شود (۱۰ تا ۱۰ تا). بعد `full_match` (گیربکس، سال دقیق، کلمات در توضیحات، تاریخ انتشار) اعمال می‌شود. آگهی‌هایی که رد شوند حذف می‌شوند و از آگهی‌های بعدی جایگزین می‌شوند تا صفحه ۱۰ تایی پر شود.
- اگر جزئیات قبلاً در `posts` باشد (مثلاً برای کاربر دیگری گرفته شده)، درخواستی زده نمی‌شود.

### دکمه «📄 ۱۰ آگهی بعدی»

- ۱۰ ردیف `queued` بعدی همین فیلتر را برمی‌دارد، جزئیات و `full_match` را انجام می‌دهد، کارت کامل می‌فرستد و `status='sent'` می‌کند.
- کارت همیشه با **آخرین نسخه** آگهی از `posts` ساخته می‌شود. اگر آگهی در این فاصله ویرایش شده باشد، کاربر نسخه جدید را می‌بیند.
- آگهی‌هایی که در این فاصله حذف شده‌اند یا دیگر مطابق فیلتر نیستند رد می‌شوند.
- وقتی صف تمام شد: «✅ همه آگهی‌ها نمایش داده شد. از این به بعد آگهی‌های جدید خودکار ارسال می‌شوند.»

### دکمه «📋 فهرست خلاصه همه»

همه آگهی‌های باقی‌مانده را در پیام‌های فشرده (هر پیام `SUMMARY_LIST_SIZE` آگهی، با داده‌های لیست و بدون درخواست جزئیات) می‌فرستد و `status='listed'` می‌کند:

```
📋 آگهی‌های «دنا اتومات مشهد» (۱ از ۹)

۱. دنا پلاس توربو اتومات ۱۴۰۲ — ۳٬۵۰۰ کیلومتر — ۱٫۱۵ میلیارد — ۲ ساعت پیش — مشاهده
۲. دنا پلاس اتومات ۱۴۰۱ — ۲۸٬۰۰۰ کیلومتر — ۹۸۰ میلیون — ۵ ساعت پیش — مشاهده
...
```

«مشاهده» لینک آگهی در دیوار است.

### نکات

- اگر به سقف `BACKFILL_MAX_PAGES` رسیدیم و هنوز به تاریخ مرز نرسیده بودیم، در پیام جمع‌بندی گفته می‌شود: «به‌دلیل تعداد زیاد، آگهی‌های تا تاریخ X پوشش داده شد؛ برای نتیجه کامل‌تر فیلتر را دقیق‌تر کنید.»
- آگهی‌های `queued` جزو «دیده‌شده» حساب می‌شوند؛ Crawler آن‌ها را دوباره به‌عنوان آگهی جدید نمی‌فرستد، و برای آن‌ها اعلان تغییر هم ارسال نمی‌شود (کاربر هنوز آن‌ها را ندیده).
- اگر Crawler همزمان با Backfill آگهی جدیدی پیدا کند، کلید یکتای `deliveries` جلوی تکرار را می‌گیرد.
- ارسال کارت‌ها با ۱ ثانیه فاصله است (محدودیت تلگرام برای هر چت).

## تغییر آگهی بعد از ارسال

فروشنده ممکن است بعد از اینکه آگهی برای کاربر ارسال شده، قیمت را عوض کند، توضیحات را ویرایش کند یا آگهی را حذف کند. ربات این تغییرات را تشخیص می‌دهد و بسته به نوع تغییر رفتار می‌کند.

### تشخیص تغییر

| منبع | هزینه | فاز | توضیح |
|---|---|---|---|
| **نتایج جستجوی Crawler** | رایگان | ۱ | Crawler هر ۱۰ دقیقه به هر حال لیست را می‌گیرد. اگر توکنی که در `posts` داریم دوباره دیده شود (مثلاً بعد از نردبان) و قیمت یا عنوان لیست با نسخه ذخیره‌شده فرق کند، جزئیات دوباره گرفته می‌شود. |
| **بررسی دوره‌ای** (`services/recheck.py`) | درخواست اضافه | ۲ | فقط برای آگهی‌هایی که به کسی `sent` شده‌اند و کمتر از `RECHECK_MAX_AGE_DAYS` عمر دارند. هر `RECHECK_INTERVAL_HOURS` یک بار، با سقف `RECHECK_MAX_REQUESTS` درخواست، به ترتیب قدیمی‌ترین `last_checked_at`. |

    ...

def diff(old: Post, new: Post) -> list[Change]:

اگر `fingerprint` عوض نشده باشد (مثلاً نردبان بدون تغییر)، کاری انجام نمی‌شود. اگر `get_post` پاسخ «آگهی حذف شده» یا 404 بدهد، `status='deleted'` و یک تغییر از نوع `deleted` ثبت می‌شود.

### رفتار برای هر نوع تغییر

| تغییر | رفتار ربات | دلیل |
|---|---|---|
| 📉 **کاهش قیمت** (بیش از آستانه) | **پیام جدید** در جواب (reply) به پیام قبلی: «📉 قیمت کاهش یافت: ۲٫۹۵ ← ۲٫۸۰ میلیارد (−۵٪)» + ویرایش بی‌صدای پیام قبلی | مهم‌ترین اتفاق برای خریدار و بنگاه‌دار و ارزش افزوده اصلی ربات |
| 📉 کاهش قیمت (کمتر از آستانه) | فقط ویرایش بی‌صدای پیام قبلی | ارزش اعلان ندارد |
| 📈 **افزایش قیمت** | ویرایش بی‌صدای پیام قبلی (قیمت جدید + «✏️ ویرایش شد») | ارزش اعلان ندارد، ولی اطلاعات قبلی نباید غلط بماند |
| ✏️ **تغییر توضیحات، کارکرد یا عکس** | ویرایش بی‌صدای پیام قبلی | همان دلیل |
| 🎯 **آگهی بعد از تغییر وارد فیلتر شد** (مثلاً قیمت زیر سقف کاربر رفت) | **مثل آگهی جدید** ارسال می‌شود با برچسب «📉 قیمت کاهش یافت و وارد فیلتر شما شد» | کاربر قبلاً این آگهی را ندیده |
| 🚫 **آگهی بعد از تغییر از فیلتر خارج شد** | اعلانی ارسال نمی‌شود؛ فقط ویرایش بی‌صدای پیام قبلی | اعلان «دیگر مناسب شما نیست» فقط مزاحمت است |
| ❌ **آگهی حذف یا فروخته شد** | ویرایش بی‌صدای پیام قبلی: «❌ این آگهی دیگر در دیوار موجود نیست» | کاربر وقتش را برای تماس هدر نمی‌دهد |
| 🔝 **نردبان بدون تغییر** | هیچ کاری | همان آگهی است |

**تنظیم هر فیلتر (`change_alerts`)** فقط روی **اعلان‌ها** اثر دارد؛ ویرایش بی‌صدای پیام‌ها همیشه انجام می‌شود تا اطلاعات غلط نماند:

| مقدار | اعلان‌ها |
|---|---|
| `price_drop` (پیش‌فرض) | فقط کاهش قیمت بیش از آستانه |
| `all` | کاهش قیمت + هر ویرایش دیگر + حذف آگهی (reply کوتاه، مثل «✏️ کارکرد: ۳٬۵۰۰ ← ۴٬۲۰۰») |
| `none` | هیچ |

### جلوگیری از اسپم

- **آستانه:** اعلان کاهش قیمت فقط اگر کاهش ≥ `PRICE_DROP_MIN_PERCENT` (۱٪) **یا** ≥ `PRICE_DROP_MIN_AMOUNT` (۱۰ میلیون تومان) باشد.
- **مبنای مقایسه `sent_price` است** (قیمتی که کاربر دیده)، نه قیمت قبلی. پس کاهش‌های کوچک پشت سر هم جمع می‌شوند و وقتی از آستانه گذشتند اعلان داده می‌شود.
- **Cooldown:** حداکثر یک اعلان برای هر آگهی و هر کاربر در `CHANGE_ALERT_COOLDOWN_HOURS` (۶ ساعت).
- بعد از هر اعلان، `sent_price` و `last_notified_at` به‌روز می‌شوند.
- اگر یک آگهی در یک اجرا چند تغییر داشت، همه در **یک** پیام و یک ویرایش جمع می‌شوند.

### منطق `services/changes.py`

```
handle_changes(post, changes):
  for d in deliveries where post_token = post.token and status in ('sent', 'listed'):
      f = d.filter
      still_matches = full_match(post, f)

      # ۱. ویرایش بی‌صدا (همیشه، اگر message_id داریم)
      if d.message_id: sender.edit(d, format_card(post, edited=True, deleted=post.status == 'deleted'))

      # ۲. اعلان
      if f.change_alerts == 'none' or in_cooldown(d): continue
      if price_drop_significant(d.sent_price, post.price) and still_matches:
          sender.reply(d, format_price_drop(d.sent_price, post.price))
      elif f.change_alerts == 'all':
          sender.reply(d, format_change_summary(changes))
      else:
          continue
      d.sent_price = post.price; d.last_notified_at = now
```

- برای ردیف‌های `listed` (بدون `message_id`) ویرایشی انجام نمی‌شود و اعلان کاهش قیمت به‌صورت پیام مستقل (بدون reply) ارسال می‌شود.
- حالت «آگهی وارد فیلتر شد» جدا از این تابع و در مرحله `full_match` خود Crawler مدیریت می‌شود (آن کاربر ردیفی در `deliveries` ندارد).

### نمونه پیام کاهش قیمت

```
↩️ (در جواب به پیام آگهی قبلی)

📉 کاهش قیمت!
🚗 دنا پلاس توربو اتومات ۱۴۰۴
💰 ۲,۹۵۰,۰۰۰,۰۰۰ ← ۲,۸۰۰,۰۰۰,۰۰۰ تومان (−۵٪)
🕒 ۲۰ دقیقه پیش

[🔗 مشاهده در دیوار]
```

### محدودیت‌ها

- تشخیص از طریق Crawler فقط وقتی کار می‌کند که آگهی دوباره در نتایج جستجو ظاهر شود. اگر فروشنده ویرایش کند ولی آگهی بالا نیاید، تا فعال شدن `recheck` (فاز ۲) تغییر دیده نمی‌شود.
- اگر کاربر پیام قبلی را پاک کرده باشد، ویرایش ممکن نیست و فقط لاگ می‌شود.
- سقف `RECHECK_MAX_REQUESTS` یعنی در سیستم‌های بزرگ همه آگهی‌ها در هر دور بررسی نمی‌شوند؛ اولویت با آگهی‌هایی است که زمان بیشتری از آخرین بررسی‌شان گذشته.

## سفر کامل یک کاربر

```
1. /start                  → handlers/start: ردیف users + اشتراک آزمایشی + کیبورد اصلی
2. «➕ فیلتر جدید»          → Mini App داخل تلگرام
3. «ذخیره فیلتر»           → web_app_data → handlers/webapp: اعتبارسنجی → INSERT filters → «✅ ذخیره شد»
4. چند ثانیه بعد           → services/backfill: همه آگهی‌های بازه پیدا می‌شوند → جمع‌بندی + ۱۰ کارت اول
5. «📄 ۱۰ آگهی بعدی»       → ۱۰ کارت بعدی … تا تمام شدن صف (یا «📋 فهرست خلاصه همه»)
6. هر ۱۰ دقیقه             → services/crawler: آگهی‌های تازه مطابق → sender → 🔔
7. فروشنده قیمت را کم کرد  → crawler تغییر را می‌بیند → changes: 📉 reply به پیام قبلی
8. آگهی حذف شد             → پیام قبلی بی‌صدا «❌ دیگر موجود نیست» می‌شود
9. /edit_12                → دکمه ویرایش → Mini App پیش‌پر → UPDATE filters
10. /pause_12 یا دکمه ⏸   → active=false → planner این فیلتر را نادیده می‌گیرد
11. پایان اشتراک           → planner فیلترهای کاربر را نادیده می‌گیرد + یک بار پیام «اشتراک تمام شد»
12. بلاک کردن ربات         → sender: is_blocked=true → ارسال متوقف
```

## اجرا و استقرار

### پیش‌نیازها

- Docker و docker compose
- ربات ساخته‌شده با @BotFather
- سرور با دسترسی به `api.telegram.org` **و** `api.divar.ir` (مثل نسخه n8n)
- برای تولید: دامنه با HTTPS (Caddy یا Nginx + Let's Encrypt) برای Mini App و Webhook

> **نکته مهم محل سرور:** تلگرام در ایران فیلتر است و دیوار ممکن است IP خارجی را محدود کند. قبل از خرید سرور، از همان سرور هر دو را با `curl` تست کنید. اگر هر دو از یک سرور در دسترس نبود، دو راه دارید: پروکسی HTTP برای یکی (`HTTP_PROXY`، یا Local Bot API Server)، یا جدا کردن Fetcher روی سرور دوم (فاز بعد).

| 8 | `/pause_…` و `/resume_…` | ⏸ ← 🟢 |
| 9 | `/extend <id> -10` یا تاریخ گذشته | «اشتراک تمام شده» + توقف ارسال |
| 10 | بلاک کردن ربات و `/crawl_now` | `is_blocked=true`، بدون خطای تکراری در لاگ |
| 11 | `/del_…` | حذف |
| 12 | ری‌استارت کانتینر | هیچ آگهی تکراری ارسال نمی‌شود |

## لاگ و مانیتورینگ

- هر اجرای Crawler یک خط خلاصه لاگ می‌کند: `groups=8 pages=11 new_posts=5 details=5 matched=7 sent=7 changed=3 price_drops=1 edits=4 duration=38s`.
- اگر Crawler **دو اجرای پشت سر هم** شکست بخورد، یا پارسر برای بیش از ۵۰٪ آگهی‌ها فیلد کلیدی (قیمت/سال) پیدا نکند، به ادمین‌ها پیام هشدار ارسال می‌شود.
- اختیاری: **Sentry** برای خطاها و endpoint سلامت `/health` برای مانیتور بیرونی (مثل UptimeRobot).

## مهاجرت داده از n8n

1. در n8n → Data tables → `divar_users` و `divar_filters` را **Export CSV** کنید.
2. اجرای اسکریپت:
   ```bash
   python scripts/import_from_n8n.py users.csv filters.csv
   ```
   - `chat_id` رشته‌ای به bigint تبدیل می‌شود و فیلترها به `user_id` متصل می‌شوند.
   - `0` به `NULL` تبدیل می‌شود (بدون محدودیت).
   - نام فارسی برند با `catalog.py` به کلید انگلیسی تبدیل می‌شود.
   - کلمات با ویرگول (فارسی یا انگلیسی) به آرایه تبدیل می‌شوند.
   - **شماره فیلترها (`id`) حفظ می‌شود** تا دستورهای قبلی کاربران معتبر بمانند.
   - `change_alerts` برای همه فیلترهای منتقل‌شده `price_drop` می‌شود.
3. Workflowهای 1 و 3 و 5 را در n8n **غیرفعال** کنید. دو سیستم نباید همزمان به یک ربات وصل باشند، چون Webhook و Polling با هم تداخل دارند.
4. نسخه جدید را اجرا کنید. Crawler در اجرای اول در حالت warm-up است و چیزی نمی‌فرستد.
5. به کاربران یک broadcast بفرستید که `/start` بزنند (برای کیبورد جدید).

## محدودیت‌ها و نکات

- **API غیررسمی:** دیوار ممکن است ساختار را تغییر دهد یا IP را محدود کند. برای محصول تجاری، [پلتفرم رسمی کنار دیوار](https://kenar.divar.ir) را بررسی کنید. معماری طوری است که فقط `app/divar/` باید عوض شود.
- **احترام به دیوار:** یک client مشترک با فاصله و jitter، گروه‌بندی فیلترها، کش جزئیات، و بدون درخواست موازی.
- **شماره تماس** ذخیره یا ارسال نمی‌شود؛ کاربر از لینک آگهی آن را می‌بیند.
- **پرداخت** در فاز ۱ دستی است (کارت‌به‌کارت + `/extend`).
- **محرمانگی:** `BOT_TOKEN` و `.env` هرگز در git قرار نمی‌گیرند. اگر توکن لو رفت، در BotFather با `/revoke` عوضش کنید. فایل `n8n-api-key` پروژه قبلی را هم به این پوشه منتقل نکنید.
